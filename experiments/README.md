# resqlite Experiments

Each file documents a performance experiment: what we tried, what we measured, and whether it worked. These serve as institutional memory — before trying a new optimization, check here to see if we've already explored it.

| [268](268-stmt-cache-lazy-init.md) | Leave empty statement caches virtual | Exp 267 raised the per-connection statement cache to 128 entries and measured +0.8-1.2 MB peak RSS, attributing it to the larger fixed entry arrays. The actual 2,136-byte entry makes one cache 273,408 bytes, and optimized arm64 code revealed the more immediate cause: although `resqlite_db` is allocated with `calloc`, `stmt_cache_init` zeroed the entire array again. The compiler removed the adjacent writer clear but retained one 273,408-byte `bzero` in the reader-open loop, so a normal four-reader open eagerly touched 1,093,632 bytes before any statement used a slot. Initializing only `count = 0` is safe because lookup and cleanup inspect only entries below count and every insertion fully zeroes its slot before publishing it. Across twelve alternating-order fresh-process passes, max RSS fell 589,824 bytes at two readers and 1,056,768 bytes at four; open-growth RSS fell 540,672 and 974,848 bytes, with the candidate lower in all 48 paired observations and reader-count scaling broadly consistent with the assembly prediction. Six alternating-order AOT wall passes improved native open by 2.4% at two readers and 2.7% at four, with no candidate-slower pass above 1.6%. Full-cache and eviction controls (`point1`, `rotate128`, `churn-unique`) stayed within 0.7% in aggregate, and 23 focused tests covering empty/first-slot use, 400-statement eviction, dependency reliability and native allocation faults passed. This recovers most of exp 267's memory price with one deleted clear and no new allocation, OOM or ownership path; exact-sized dependency metadata is now justified only by a representative populated-cache footprint, not empty-open RSS. |  |
| [267](267-stmt-cache-capacity.md) | How many statements a connection can hold | Three read-path caches are keyed by SQL text and capped at 32 entries — the C per-connection prepared-statement cache, the per-worker Dart `schemaCache`, and the pool's row-size memory — and none of the three numbers had ever been measured, because every benchmark in the repo uses under ten distinct SQL strings. Exp 071 and exp 073 each rejected a cache change on exactly those grounds and each closed by asking for a `64 rotating query shapes, cache at capacity` workload before any cache-sizing experiment; neither built it, and exps 207 and 248 went after the lookup path instead, so the cache's scan has been attacked twice and its size never once. Exp 266 made the gap load-bearing two days before this run: under round-robin a sequential loop over D distinct statements was partitioned across four connections, each seeing ~D/4, and sticky dispatch sends the whole cycle to one. Because these caches evict at the front and promote on hit — approximately LRU, the worst policy for a cyclic scan — the cap is a cliff and not a slope: at D <= 32 every read hits, and at D = 33 the entry each read needs is the one the previous miss evicted. Raising all three caps to 128 is a reproduced -55.5% / -55.1% / -53.3% at 40, 64 and 128 rotating statements (14.0 us per read to 6.1 us), flat across that range exactly as a cliff predicts, with every lane inside the old cap neutral in two independent order-flipped collections and peak RSS up 0.8-1.2 MB against a ~30 MB floor. The load-bearing lane is the adversarial one: `churn-unique`, which never repeats a statement so no cache of any size can help, measured a reproduced +42.1% on the first candidate and would have rejected the raise on its own. The cause was `stmt_cache_insert` compacting the array on every eviction — `(STMT_CACHE_MAX - 1) x ~1.6 KB`, so 50 KB per prepare at 32 entries and 203 KB at 128 — identified by arithmetic (39 MB/sample of extra traffic against a measured 1.53 ms) before a second measurement was taken. Reclaiming the LRU slot in place instead, which gives up no ordering the promote-by-swap had not already given up, took the same lane to a reproduced -11.9%, because the baseline was paying ~640 us of its 3688 us sample to shift 12.8 MB. Five tests push 400 distinct statements through every cache and check each statement's identity from its result (its row, its projection, its parameter arity), since a cache returning the wrong entry is silent rather than fatal; four of the five were verified to fail against a deliberately mismatched entry. The cliff moves rather than disappears, and what bounds the next raise is the fixed-size `read_tables[64]` / `dep_columns[64]` arrays that make an entry 1.6 KB when a typical statement reads one table. |  |
| [266](266-sticky-reader-dispatch.md) | Send the read back to the worker that ran the last one | `ReaderPool._dispatch` advanced its scan cursor on every attempt, so back-to-back reads deliberately rotated across the whole pool even when it was idle. Reader workers are not interchangeable resources: each is an isolate with its own SQLite connection and page cache, its own entry in that connection's C statement cache, its own Dart schema cache and cell buffer, and its own OS thread. Round-robin therefore made all four workers independently pay for warm state the first one had already built — a fixed cost per (statement, worker) pair, invisible to every benchmark in the repo because they all execute one statement thousands of times, and very visible to an application that opens a screen, runs a query four or five times and moves on. Starting the scan at the slot that served the previous read instead of the next one is worth -32.2% on a statement's first four executions, -21.8% on its first eight and -13.2% on its first thirty-two, decaying to -1.6% by the eight-thousandth — the monotonic decay the experiment was gated on, and direct confirmation the mechanism is warm-up rather than anything per-read. A busy preferred slot still walks forward, so concurrency is untouched: four concurrent reads (+1.3%), eight against a four-worker pool (+0.2%) and a 60,000-slot result that ends its worker every sample (-0.4%) are all neutral and sign-flip between collections. Peak RSS falls where the win is (27.0 -> 26.0 MB, 29.5 -> 28.2 MB) because one worker now holds once what four held four times. `selectBytes` deliberately keeps the old rotation: exp 185's `JSON buffer reclaim` release guard rejected the first, fully-sticky version at 6.2 MB against a 512 KB budget, because exp 183's `json_buf` shrink is driven by a later small read arriving on the same connection, and stickiness never sends one to the three workers a large burst had grown. Three lines of dispatch change plus that opt-out, no public API change, three new dispatch tests. Twenty-four alternating-order lane-isolated AOT passes in two collections. | https://github.com/danReynolds/resqlite/blob/main/experiments/266-sticky-reader-dispatch.md |

| [255](255-stream-initial-emission-race.md) | Stream could emit nothing when a write raced its initial query | `db.stream()` promises to emit current results immediately, then re-emit on change. It could do neither: a stream whose initial query was still in flight when a write landed went **permanently silent**, never emitting even its first value. `StreamEngine._createStream` stored the initial result's hash as the comparison baseline and then, if the entry had been dirtied mid-flight, discarded those rows unemitted in favour of a catch-up re-query — but that re-query's `selectIfChanged` compared against the baseline taken from the very rows it replaced, found them identical, and returned 'unchanged, nothing to emit'. Initial emission suppressed as stale; replacement suppressed as unchanged; stream silent forever. The race window is the initial query's duration, so it is trivial on small tables and reliable on large ones — and opening a stream then immediately writing (seeding a list on first paint) is ordinary usage. Fix: always emit the initial result (a valid observation, and the documented contract), then re-query if dirtied; `selectIfChanged` still suppresses the follow-up when nothing changed, so no duplicate. This had been surfacing for a long time as an intermittent `write_coalescing_test` failure dismissed as a flake — at ~1-in-3 on a loaded machine — helped along by that test's own comment asserting the shape 'can't flake under load'. New regression test (40k seeded rows so the write reliably races the query) fails 0/5 without the fix and passes 6/6 with it; the old test goes 3/6 -> 8/8; 140 tests pass across the stream, write-coalescing, trigger-cascade, database and transaction suites. |  |

## Conventions

- **Experiment number:** Monotonically increasing, never reused
- **Date:** When the experiment was run (full timestamp preferred: `2026-04-14T12:30:00`)
- **Status:** `Accepted` (merged + soak window closed), `In Review` (PR open or in post-merge soak window — typically two weeks), or `Rejected` (abandoned, with explanation). New experiments start at `In Review` and graduate after the soak.
- **Commit:** Git hash of the implementing commit (added to header of each accepted experiment)

### Research Map

Scheduled experimenters should use
[`RUNNER_INSTRUCTIONS.md`](RUNNER_INSTRUCTIONS.md) as the copyable instruction
block for recurring experiment systems. Those instructions point runners at
this README, [`signals.json`](signals.json), [`JOURNAL.md`](JOURNAL.md), and
the project [`stories`](../doc/stories/) before choosing work.

`signals.json` is the canonical research map. These files are steering context,
not an allowed list. They should make prior work easy to understand without
preventing creative experiments outside the current map. A strong new
experiment can follow an active direction, revisit an area that recently looked
weak, or open a new direction entirely. The important thing is to explain why
the attempt is worth a bounded pass in light of prior work.

When an experiment changes what future work should try, de-emphasize, measure,
or watch:

- update the experiment writeup with the record of what happened
- update `signals.json` with machine-readable direction context
- add to `JOURNAL.md` only when the run surfaced a transferable lesson a
  future runner could reapply elsewhere
- leave `../doc/stories/` alone — story posts are updated on maintainer
  request, not per experiment

`signals.json` per-direction fields (see the inline `schemaNotes` block at
the top of the file for the canonical descriptions):

- `keyPriors` (required, max 6) — experiments a future runner must read.
- `archive` (optional) — older or superseded evidence; not required reading.
  Curate from `keyPriors` when a new accepted experiment supersedes an
  older one.
- `openCandidates` (optional) — dated candidate ideas waiting for the
  right workload, signal, or runner. Each item is `{idea, addedDate,
  addedAfter?, blockedOn?}`. Prune entries older than ~3 months that
  nobody picked up.
- `blockedOnMeasurement` (optional) — measurements that must land before
  the next implementation experiment in this direction is worth
  attempting. Empty if no measurement is gating new work.

### Standard Template

Use these exact headings so the experiments page can extract content automatically:

```markdown
# Experiment NNN: Title

**Date:** 2026-04-14
**Status:** Accepted / Rejected
**Direction:** `direction-id`
**Commit:** [`abc1234`](https://github.com/danReynolds/resqlite/commit/abc1234)
**Archive:** [`archive/exp-NNN`](https://github.com/danReynolds/resqlite/compare/main...archive/exp-NNN)

## Problem

What performance issue or opportunity was identified.

## Hypothesis

The proposed optimization and why it should work.

## Approach

What was built or changed. Implementation details.

## Results

Benchmark measurements. Use markdown tables for comparisons.

## Decision

Why accepted or rejected. Trade-offs considered.

## Future Notes

Optional. Short notes for future experimenters: adjacent prior work, what would
make the area interesting again, or what to measure before revisiting.
```

Header fields:

- **Commit** — required for Accepted experiments; points at the merged
  implementation commit on main.
- **Archive** — added for Rejected experiments *whose implementation is
  worth preserving for future re-evaluation* (the common case when the
  rejection reason is "below noise floor, not worth the complexity").
  Points at a git tag (`archive/exp-NNN`) that pins the last commit of
  the experiment branch before it was deleted. See the
  `resqlite-experiment` skill for the tagging workflow. Skip this field
  for rejections of the form "implementation was broken" — there's
  nothing worth preserving.

Older experiments use varied headings (`What We Built`, `Changes`, `Benchmark`, `Why Accepted`, etc.) — those still work, but new experiments should follow this template.
