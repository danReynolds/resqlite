# resqlite Experiments

Each file documents a performance experiment: what we tried, what we measured, and whether it worked. These serve as institutional memory — before trying a new optimization, check here to see if we've already explored it.

## Accepted

Experiments that proved their value and were merged into the codebase.

| [260](260-result-list-presize.md) | Size the result buffer from what the SQL returned last time | `decodeQuery` starts every result at 256 rows' worth of `List<Object?>` slots and doubles when it overflows. Growing that list copies every live element with a store barrier into a freshly faulted array, so a 200k-slot result copies ~322k slots through ~5 MB of immediate garbage on its way up. A standalone AOT reproduction of the decode loop puts the doubling at 2318 us against 865 us pre-sized, with the loads, switch and stores together under 500 us — so buffer growth, not cell decoding, is most of what exp 251 measured as `Dart result construction` (2524 us of 5124 us worker wall on the same shape). `ReaderPool` now remembers each SQL's result size on the main isolate and stamps it onto the request; the worker consults it only when the buffer overflows, so a result that fits inside the initial allocation runs byte-identical code. Two design points carry it: the memory cannot live in the worker, because a result over `sacrificeSlotThreshold` ends the isolate that produced it and a worker-local hint dies exactly when it was worth having (that first version won 30-35% on mid-sized reads and ~1% on the largest); and the hint sizes growth rather than the initial allocation, because an early version that sized the allocation made a `LIMIT ?` statement alternating 8000/50 rows 2.8x slower on its small leg. Focused AOT A/B, two order-flipped passes, `ab_drift_check` REPRODUCED on every primary: 10k x 20 INTEGER -25.1% / -24.8%, 5k x 4 INTEGER -32.2% / -33.7%, and the repo's canonical 6-column product row x 10k -33.6% / -32.3% (3.5 ms -> 2.3 ms). Both controls return fewer rows than the initial buffer holds, so the changed path is unreachable and they move opposite signs inside the 3% floor; both mispredict guards are neutral by construction. Memory was not measured; arithmetic on the allocation path says total bytes allocated fall 14-61% everywhere (the intermediate arrays stop existing) but peak capacity is not a guaranteed improvement — 23.7% smaller on all three primary lanes, yet 22-25% larger for a result that lands just under a doubling boundary, as `mixed6-1k` does. This closes exp 059 as wrongly rejected rather than re-tested: its rejection reason was the April release suite's noise floor, its mechanism claim that `list growth is already cheap` is false, and it sized the initial allocation — carrying exp 067's small-query regression inside the same change. |  |
| [259](259-native-ascii-text-flag.md) | Native TEXT ASCII classification for the row decoder | `decodeQuery` cannot build a Dart `String` from a TEXT cell until it knows whether the payload is pure ASCII (`String.fromCharCodes` widen) or not (`utf8.decode`), and it was answering that itself: a second `ExternalTypedData` word view plus a bounds-checked scan per cell, degrading to a byte-by-byte loop for anything under 16 bytes — which is most database text. `resqlite_step_row` already holds the pointer and length one frame earlier, where the same question is a branch-free SWAR pass over bytes still in cache. Moved it there: `text_is_ascii` reports `RESQLITE_TEXT_ASCII` (type code 6, the first value SQLite's 1-5 leaves free) and the decoder's TEXT arm splits into a widen path and a straight-to-`utf8.decode` path with no scan of its own. The stream hash is untouched — `resqlite_step_row_hash` folds the local `SQLITE_TEXT` before the switch, so the canonical digest still matches `resqlite_query_hash` (the exp 228 invariant). Focused AOT A/B, two order-flipped passes, `ab_drift_check` REPRODUCED on every primary lane: 10k x 8 short ASCII TEXT -12.3% / -10.4%, 40 B -14.3% / -10.7%, 2k x 4 400 B -22.2% / -19.4%, and the repo's canonical 6-column mixed product row (`id` INTEGER + 4 TEXT + REAL, taken verbatim from `benchmark/shared/seeder.dart`) -24.4% / -19.2%. The two neutral lanes carry the verdict: the INTEGER-only control runs byte-identical code in both arms and moves +0.2% / -2.9% (opposite signs, inside the 3% floor), ruling out the exp 254 per-worktree binary offset; and the CJK guard is -2.4% / -1.7%, confirming that scanning a non-ASCII value to the end in C costs less than the partial Dart scan it replaced. A `resqlite_test_text_is_ascii` differential test plus an every-offset multibyte `select()` round trip gate the classification, since a wrong answer is silent mojibake rather than a crash. |  |
| [256](256-stale-initial-emission-tradeoff.md) | Stale-then-correct vs suppress-stale initial stream emission | Exp 255 guaranteed a stream always emits; this settles WHICH rows the first emission carries when a write raced the initial query. Lane A emits the known-superseded initial rows immediately and corrects via the catch-up re-query; lane B suppresses that emission, poisons the comparison baseline so the re-query is guaranteed to emit, and lets the corrected result be the stream's first. A's advantage — a faster first emission — is measured against the wrong clock: what a subscriber cares about is time-to-CORRECT-value, and the catch-up re-query runs in both lanes. Measured across race windows widened by seed size: B costs **~1.4 ms at 20k rows and ~0.4 ms at 60k** on time-to-correct (8.1 -> 9.5 and 18.5 -> 18.9 p50) and removes the stale frame **entirely** (1.00 -> 0.00 per raced stream at every size); A renders exactly one wrong frame on every raced stream, the list-jump artifact a reactive stream exists to prevent. The no-race control is identical in both lanes (13.3 ms, 2 emissions), confirming the change is scoped to the raced path. **Accepted: ship B.** It is not a return to the exp 255 bug — that was suppression WITHOUT poisoning, which let the initial emission and its replacement cancel each other; the sentinel baseline guarantees an emission and `_requery` propagates errors, so a stream always resolves to a value or an error. Would revisit only for a skeleton-UI workload that prefers stale rows to nothing, which is an opt-in public-API question rather than a default. |  |
| [255](255-stream-initial-emission-race.md) | Stream could emit nothing when a write raced its initial query | `db.stream()` promises to emit current results immediately, then re-emit on change. It could do neither: a stream whose initial query was still in flight when a write landed went **permanently silent**, never emitting even its first value. `StreamEngine._createStream` stored the initial result's hash as the comparison baseline and then, if the entry had been dirtied mid-flight, discarded those rows unemitted in favour of a catch-up re-query — but that re-query's `selectIfChanged` compared against the baseline taken from the very rows it replaced, found them identical, and returned 'unchanged, nothing to emit'. Initial emission suppressed as stale; replacement suppressed as unchanged; stream silent forever. The race window is the initial query's duration, so it is trivial on small tables and reliable on large ones — and opening a stream then immediately writing (seeding a list on first paint) is ordinary usage. Fix: always emit the initial result (a valid observation, and the documented contract), then re-query if dirtied; `selectIfChanged` still suppresses the follow-up when nothing changed, so no duplicate. This had been surfacing for a long time as an intermittent `write_coalescing_test` failure dismissed as a flake — at ~1-in-3 on a loaded machine — helped along by that test's own comment asserting the shape 'can't flake under load'. New regression test (40k seeded rows so the write reliably races the query) fails 0/5 without the fix and passes 6/6 with it; the old test goes 3/6 -> 8/8; 140 tests pass across the stream, write-coalescing, trigger-cascade, database and transaction suites. |  |

| [246](246-slot-sacrifice-guard.md) | Slot-count sacrifice trigger — fix the string misroute | The reader sacrifices a row result (Isolate.exit zero-copy, at the cost of a reader respawn) when its estimated BYTES exceed 256 KB. Exp 245 measured that this asks the wrong question: `SendPort.send`'s cost tracks the MUTABLE flat-list SLOT COUNT (rows x cols), not payload bytes — strings/immutable leaves are shared on send for free. So a result large in bytes but small in slots (a few rows with a big TEXT/BLOB column — base64 blobs, large JSON/text docs) is cheap to send yet gets SACRIFICED, paying a reader respawn for a copy that never happens. Exp 246 routes the decision on slot count (`raw.values.length`) instead: `_shouldSacrifice` = `values.length > sacrificeSlotThreshold` (default 32*1024 = the exact all-integer equivalent of the 256 KB byte threshold at 8 bytes/cell). End-to-end A/B: the misroute shape (4 rows x 100 KB string) stops sacrificing (1.00 -> 0.00 sacrifices/select) and runs **31% faster** (131 -> 91 us) — every such read previously killed+respawned a reader for nothing; every numeric/structural shape (band 40k, large 200k, medium 20k, small) is byte-for-byte the same routing at parity latency. Threshold is measured, not guessed: the ~48k INTRINSIC crossover (exp 245) regressed the 40k-slot band (+12%, sent something that should sacrifice) because end-to-end the send copy is on the worker's critical path (exp 244), so the crossover arrives earlier; 32k = the byte trigger's all-int equivalent restores band parity while keeping the string fix. Slot count is also free (the flat list's length, no per-cell accounting), so the change is a net **simplification**: the byte machinery it replaced — the byte threshold, `RawQueryResult.estimatedBytes`, and the decoder's per-cell `byteEstimate` — was deleted in the same change, having no readers left once routing moved to slot count. That includes exp 236's `transferableBytes` subtraction, since blob size can no longer influence the decision (exp 236's blob-cell TransferableTypedData wrapping itself is unaffected and still ships). The shippable payoff of the send-vs-sacrifice arc (exp 241 confound -> 244 pool -> 245 intrinsic -> 246 fix). |  |

## Conventions

- **Experiment number:** Monotonically increasing, never reused
- **Date:** When the experiment was run (full timestamp preferred: `2026-04-14T12:30:00`)
- **Status:** `Accepted` (merged + soak window closed), `In Review` (PR open or in post-merge soak window — typically two weeks), or `Rejected` (abandoned, with explanation). New experiments start at `In Review` and graduate after the soak.
- **Commit:** Git hash of the implementing commit (added to header of each accepted experiment)

### Research Map

Scheduled experimenters should use
[`RUNNER_INSTRUCTIONS.md`](RUNNER_INSTRUCTIONS.md) as the copyable instruction
block for recurring experiment systems. Those instructions point runners at
this README, [`signals.json`](signals.json), [`JOURNAL.md`](JOURNAL.md), and
the project [`stories`](../doc/stories/) before choosing work.

`signals.json` is the canonical research map. These files are steering context,
not an allowed list. They should make prior work easy to understand without
preventing creative experiments outside the current map. A strong new
experiment can follow an active direction, revisit an area that recently looked
weak, or open a new direction entirely. The important thing is to explain why
the attempt is worth a bounded pass in light of prior work.

When an experiment changes what future work should try, de-emphasize, measure,
or watch:

- update the experiment writeup with the record of what happened
- update `signals.json` with machine-readable direction context
- add to `JOURNAL.md` only when the run surfaced a transferable lesson a
  future runner could reapply elsewhere
- leave `../doc/stories/` alone — story posts are updated on maintainer
  request, not per experiment

`signals.json` per-direction fields (see the inline `schemaNotes` block at
the top of the file for the canonical descriptions):

- `keyPriors` (required, max 6) — experiments a future runner must read.
- `archive` (optional) — older or superseded evidence; not required reading.
  Curate from `keyPriors` when a new accepted experiment supersedes an
  older one.
- `openCandidates` (optional) — dated candidate ideas waiting for the
  right workload, signal, or runner. Each item is `{idea, addedDate,
  addedAfter?, blockedOn?}`. Prune entries older than ~3 months that
  nobody picked up.
- `blockedOnMeasurement` (optional) — measurements that must land before
  the next implementation experiment in this direction is worth
  attempting. Empty if no measurement is gating new work.

### Standard Template

Use these exact headings so the experiments page can extract content automatically:

```markdown
# Experiment NNN: Title

**Date:** 2026-04-14
**Status:** Accepted / Rejected
**Direction:** `direction-id`
**Commit:** [`abc1234`](https://github.com/danReynolds/resqlite/commit/abc1234)
**Archive:** [`archive/exp-NNN`](https://github.com/danReynolds/resqlite/compare/main...archive/exp-NNN)

## Problem

What performance issue or opportunity was identified.

## Hypothesis

The proposed optimization and why it should work.

## Approach

What was built or changed. Implementation details.

## Results

Benchmark measurements. Use markdown tables for comparisons.

## Decision

Why accepted or rejected. Trade-offs considered.

## Future Notes

Optional. Short notes for future experimenters: adjacent prior work, what would
make the area interesting again, or what to measure before revisiting.
```

Header fields:

- **Commit** — required for Accepted experiments; points at the merged
  implementation commit on main.
- **Archive** — added for Rejected experiments *whose implementation is
  worth preserving for future re-evaluation* (the common case when the
  rejection reason is "below noise floor, not worth the complexity").
  Points at a git tag (`archive/exp-NNN`) that pins the last commit of
  the experiment branch before it was deleted. See the
  `resqlite-experiment` skill for the tagging workflow. Skip this field
  for rejections of the form "implementation was broken" — there's
  nothing worth preserving.

Older experiments use varied headings (`What We Built`, `Changes`, `Benchmark`, `Why Accepted`, etc.) — those still work, but new experiments should follow this template.
