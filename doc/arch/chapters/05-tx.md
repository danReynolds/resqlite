A transaction holds the writer for the duration of its body. Nesting maps onto SQLite savepoints ([[test:test/transaction_test.dart#db.transaction() inside a transaction nests via savepoint@1lvw]]). The callback runs on the **main** isolate, not the worker — deliberately, because shipping a closure to another isolate would require every captured object to be sendable, a constraint that is trivially violated by accident and produces confusing failures at runtime rather than helpful ones at compile time. So `tx.execute` and `tx.select` are ordinary async calls that each round-trip to the writer, and the callback stays ordinary Dart code.

Reads inside a transaction run on the *writer's* connection rather than the reader pool, because uncommitted writes are visible only to the connection that made them ([[test:test/transaction_test.dart#db.select() inside a transaction sees uncommitted writes@1nrc]]).

## The floor that shapes everything

This subsystem's measured truth is humbling, and it has closed more experiments than any other area: **the per-statement isolate round trip dominates transaction control**, and almost every clever optimization dissolves against it.

Caching control statements was a genuine win — top-level transaction control had real prepare/finalize work to remove [[101.1]]. After that, the record is a sequence of well-reasoned ideas that measured below the floor:

Savepoint string allocation is below the decision threshold even at 50 savepoints per iteration, a deliberately worst-case shallow fan-out [[111.1]]. Compressing savepoint names to reuse cached SQL moved best-case control rows 6–17%, but the representative nested-write fanout — the row that actually matches production shape — failed to reproduce across the order flip [[189.1]]. Lazy savepoint materialization helped only empty transaction bodies, and fusing `SAVEPOINT` with the first execute regressed the meaningful shape in both pass orders [[212.1]].

The most instructive rejection is the last one. Buffering `Future.wait([tx.execute × N])` into a single envelope against the open transaction *worked* — it removed the round-trip floor for that shape and measured a real improvement. It was rejected anyway, on the grounds that the pattern has no idiomatic home in the API: same-SQL bulk atomic writes belong on `executeBatch`, which already runs the whole matrix in C, and different-SQL bursts are covered by standalone coalescing [[213.1]]. Optimizing a pattern the library does not want to encourage would have made that pattern faster and more attractive at once.

## What that implies

If transaction control ever needs to get materially faster, the target is the round-trip floor itself — not the statements around it. That means something structural: a protocol that lets a bounded, statically-known sequence cross once, without inviting callers into an anti-pattern. Nothing currently justifies it; the record above exists so the next attempt starts from the floor rather than rediscovering it.
