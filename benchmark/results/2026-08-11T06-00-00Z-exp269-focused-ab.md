# Experiment 269: enforced-bound inline reads

Collected 2026-08-11 on arm64 macOS 26.2 (Apple M1 Pro) with Dart 3.12.2.
Baseline is `origin/main` at `96e6730`; the candidate runs a `select()` on the
calling isolate when the pool's per-SQL memory says it is small, under three
caps enforced against what the query actually produces, plus a per-event-loop-turn
time budget. Both arms were built as native-asset-aware AOT CLI bundles from an
identical harness source, so the decode path is AOT-compiled (exp 193's
requirement) and only `lib/`, `native/` and `hook/` differ:

```console
dart build cli   # entry point copied to bin/, one relative import rewritten
<arm>/bundle/bin/select_inline_dispatch --lane=<lane> --warmup=5 --samples=<n>
```

The harness source is
[`benchmark/experiments/select_inline_dispatch.dart`](../experiments/select_inline_dispatch.dart),
extended here with the three lanes exp 265's rejection said a successor needs.
Every lane is **lane-isolated** — one fresh process per lane per arm — and
passes alternate collection order (odd baseline-first, even candidate-first).

Values are microseconds per sample. `frame-jitter` is the exception: its sample
value is the **worst lateness a 60 Hz timer suffered** during the sample, so it
is a latency rather than a duration, still read as lower-is-better.

## Three collections

Collections 1 and 2 measured the first candidate, whose decode-loop cap checks
were guarded by `cap != 0 &&`. Collection 3 measured the final one, which passes
a `noInlineCap` sentinel instead so the guard is a single unconditional compare.
Only `mixed6-1k` — the one control with four TEXT cells per row — distinguishes
them, which is the point of keeping all three tables.

## The `mixed6-1k` control, and what it is actually reading

`mixed6-1k` returns 1,000 rows, four hundred times the row cap, so it cannot
reach the changed routing path in either arm. It nonetheless moved +4.5% and
+4.6% in the first two collections, above the 3% effect floor and in the same
direction in seven of eight passes.

Two things were done about it.

**Priced against a binary that changes nothing else.** A third build — plain
`origin/main` with `SQLITE_OMIT_PROGRESS_CALLBACK` removed and no other change —
was run against `origin/main` over four order-flipped passes:

| lane | p1 | p2 | p3 | p4 | mean |
|---|---|---|---|---|---:|
| `point1` | −3.6% | +3.2% | +0.3% | −1.1% | **−0.31%** |
| `mixed6-1k` | +34.9% | +7.0% | +1.3% | +1.8% | **+11.27%** |
| `int20-10k` | −2.4% | −2.3% | −3.1% | −0.9% | **−2.19%** |
| `page64` | −0.2% | −0.5% | +2.1% | −1.2% | **+0.07%** |
| `scan-count` | +0.4% | +5.4% | +0.5% | +5.0% | **+2.84%** |

Compiling the progress callback back in adds one `nVmStep >= nProgressLimit`
compare at the VDBE's jump-back opcodes and nothing else. `int20-10k`, the lane
that runs by far the most opcodes, comes out **faster**, which is not a
direction added work can produce — so this is binary layout, the exp 254 trap,
and the flag itself is below the floor. `mixed6-1k` reads +34.9% in one pass of
that inert comparison, which is the number to hold against its +4.5%.

**Reduced at the source anyway.** The guarded form of the cap checks
(`inlineByteCap != 0 && (inlineBytes += textLen) > inlineByteCap`) executes in
the decode loop shared with every worker read, four times per row on this lane.
Replacing the zero-guard with a `noInlineCap` sentinel makes it one
unconditional compare, and collection 3 measures `mixed6-1k` at **+2.8%** with
one pass negative and one of the two verdicts neutral. The residue is at the
floor and is not separable from layout, but the direction is what the mechanism
predicts and the change is free.

## Is the per-turn budget doing anything?

A fourth build, identical to the candidate except that
`inlineTurnBudgetUs` is raised to `1 << 40` (never reached), against baseline and
the shipped candidate, four order-flipped passes, lane-isolated:

| lane | dispatch (baseline) | budgeted (candidate) | unbudgeted |
|---|---:|---:|---:|
| `frame-jitter` worst frame lateness | 2381 us | **1147 us** | **33344 us** |
| `frame-jitter` p90 | 2415 us | 1597 us | 33347 us |
| `point1` | 1097 us | 410 us | 399 us |

33,344 us is two 60 Hz frame intervals to within 10 us: with no budget the read
chain holds the event loop for the whole 50 ms sample and the frame timer misses
every deadline in it. This is exp 265's third objection, reproduced exactly as
it predicted and at a magnitude — 14x worse than dispatch — that would have
sunk the design on its own.

The budget removes it completely, and costs 2.8% of the throughput win
(410 us against 399 us on `point1`). Budgeted inline is also **better than
dispatch**, which was not predicted: the dispatch arm answers roughly 6,000
reads in the 50 ms window and every reply is a port message whose microtask
chain competes with the timer, where the candidate serves most reads without
waking the event loop at all and yields on a bounded 1 ms cadence.

## Routing, verified directly

`test/inline_read_routing_test.dart` asserts the route of individual reads
through the pool's `inlineSelectTotal` / `inlineAbortTotal` /
`inlineTurnYieldTotal` counters, which is the only surface that distinguishes an
inline read from a dispatched one.

| statement | route |
|---|---|
| `SELECT * FROM items WHERE id = ?` (3rd execution) | inline |
| same statement, 1st and 2nd execution | dispatch |
| `SELECT count(*) FROM items` over 20,000 rows | inline |
| `SELECT * FROM photos WHERE id = ?`, one 5 MB blob | **abort** (byte cap) |
| `SELECT count(*) FROM items WHERE note LIKE '%1234%'` | **abort** (VM-step cap) |
| `SELECT * FROM items ORDER BY name LIMIT 10`, unindexed | **abort** (VM-step cap) |
| `SELECT * FROM items LIMIT ?` armed at 1, run at 256 | **abort** (row cap) |
| `SELECT * FROM items LIMIT 400` | never attempted (row high-water) |
| any statement that has aborted once | never attempted again |

Per [EXP-267]'s rule, these were checked against a build with enforcement
removed rather than trusted because they passed: with the byte and VM-step caps
disabled, the three cap tests and `an aborted statement is not attempted again`
fail on the counter while still passing on the returned data — which is the
failure mode being guarded, since an unbounded inline read returns correct rows.

## Memory

`benchmark/shared/memory_probe.dart` (exp 261), `maxRss`, one process per lane.
Peak RSS is **+0.8 to +1.2 MB** on every small-read lane across all three
collections, which is the fifth reader connection `Database.open` now allocates
for the calling isolate — a per-connection page cache and statement cache
against a ~30 MB floor. `point-under-load` and `point1-wide20` come out slightly
*lower* in some collections; `blob1-5mb` moves +2 to +7 MB but with a spread far
wider than the difference, and it is the lane whose 5 MB rows dominate the
reading.

## Environment

Load average 5.0 at the start of collection 1, on a host with other work
running throughout — the third consecutive experiment under claim 264.6's
conditions. The order-flipped design and the two mechanically-inert controls
carry it: `int20-10k` is within ±2.1% in every collection and `blob1-5mb` and
`scan-count` sign-flip inside ±1.2%, while the primaries reproduce within a few
points of each other across three collections taken an hour apart.
