## Round 1 & 2 (initial prototype, superseded)

Round 1 (single-function inline NEON branch) and round 2 (separate
`json_write_base64_scalar` / `_neon` functions dispatched from
`json_write_base64`) both reproduced the 4 KB / 128 B wins at similar
magnitudes but broke the 3 B / mixed lanes at +3-9 % reproduced. Splitting
functions traded inline-code layout for indirection cost per call (~5-10
cycles × ~80k calls per query on the 3 B lanes ≈ 400 µs / query, matching
the observed regression). The kept round-3 refactor puts the NEON bulk in
its own `noinline` function while inlining the scalar body back into
`json_write_base64`, so the small-blob path is byte-identical to exp 225's
scalar layout and the 3 B regression collapses back to noise.

## Test verification

- `dart test test/database_test.dart -n selectBytes` — 9/9 tests pass on
  candidate, including `Database selectBytes encodes blobs as base64` (the
  BLOB round-trip that would surface any bit-level difference).
- Bit-level output identity between scalar and NEON kernels follows from
  the algebraic equivalence: `vld3q_u8` produces 16 lanes of (A,B,C)
  triplets per iteration; the shift/mask/or sequence maps identically to
  the scalar `v >> 12` / `v & 0xFFF` extractions; `vqtbl4q_u8` on a
  64-byte alphabet is the vector form of `b64_table[idx]`; `vst4q_u8`
  interleaves in the same char order the scalar `memcpy(pair_table, 2)`
  path emits.
