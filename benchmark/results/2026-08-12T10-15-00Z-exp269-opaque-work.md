## Question

Do the candidate's 64-row, 64 KiB payload, 10,000-opcode, and 1 ms turn limits
bound a read whose expensive work occurs inside one SQLite opcode?

The SQL returns one small INTEGER and copies no payload:

```sql
SELECT length(randomblob(?)) AS n
```

Each process first executed the statement twice with a one-byte parameter so
the candidate's per-SQL history admitted the third execution. The timed samples
used 16,777,216 bytes. A 1 ms timer was scheduled immediately before each
`select()`; the receipt records whether it fired before the future completed.

## Interpretation

The SQLite work is neutral in wall time: 26-28 ms in both arms. The scheduling
effect is categorical. Current main dispatches the query, so the calling isolate
can run the 1 ms timer while the worker is busy. The candidate runs the same
query synchronously on the caller; the timer cannot fire until the full native
call returns.

This is more than a 25x overrun of the nominal 1 ms per-turn budget, proving it
cannot cap one read, without crossing a row, result-payload, or VM-opcode cap.
The VM progress handler counts SQLite instructions between callbacks; it cannot
preempt work hidden inside one instruction. Exp 269's safety premise is
therefore refuted even though its small-read throughput measurements remain
valid. The corrected branch restores worker-first behavior and reproduces the
responsive timer result.
