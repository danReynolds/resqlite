# Exp 240 — batched i64 → decimal encode (moonshot, rejected)

Two focused measurements, both on Apple Silicon (arm64, macOS):

1. **Isolated conversion microbench** —
   [`benchmark/experiments/i64_batch_encode.dart`](../experiments/i64_batch_encode.dart).
   Formats one 200-value i64 array to a comma-separated decimal string per
   call, timing only the conversion (no JSON tokens, no SQLite). Compares the
   shipped per-value two-digit-LUT formatter (`scalar`) against two batched
   candidates: a 2-way software-pipelined scalar (`pipe2`) and an inlined NEON
   vector digit kernel over the array (`neon`). Median ns per array pass;
   percentages are vs `scalar`.

2. **End-to-end selectBytes A/B** — the pipelined-scalar candidate wired into
   `write_json_to_buf`'s `SQLITE_INTEGER` arm (adjacent integer cells formatted
   as a pipelined pair), against `origin/main` at `8c3ada9`, using the existing
   [`benchmark/experiments/select_bytes_int_heavy.dart`](../experiments/select_bytes_int_heavy.dart).
   Four interleaved passes; table shows median-of-medians µs/query.

## 1. Isolated conversion microbench (3 stable passes, representative)

| Lane | scalar | pipe2 | neon |
|---|---:|---:|---:|
| big ~19–20 digit  | 2258 ns | **−6.6%** | **−16.8%** |
| mid ~10 digit     |  947 ns | **−9.7%** | +57.6% |
| small 0..9999     |  960 ns | +5.3%     | +48.9% |
| mixed magnitudes  | 1159 ns | −1.4%     | +0.9% |

`pipe2` reproduces a −6 to −13 % win on mid/big magnitudes across passes and is
roughly flat on short/mixed. `neon` wins only on the longest chain (−15 to
−20 % on 20-digit BIGINTs) and is a **disaster on realistic short values**
(+45 to +60 %): the fixed vector setup can't amortise below ~9 digits. This is
exp 231's per-value finding reproduced *with an array in hand* — the reopen
condition exp 231 named — so the NEON reopen door is closed harder, not opened.

## 2. End-to-end selectBytes A/B (median of 4 interleaved passes)

| Lane | Baseline | Candidate | Delta |
|---|---:|---:|---:|
| 10k × 20 small non-neg (0..9999) | 4918 | 5309 | **+7.9%** |
| 10k × 8 small non-neg (0..9999)  | 2371 | 2421 | +2.1% |
| 10k × 8 small ints               | 2624 | 2792 | +6.4% |
| 10k × 20 small ints              | 5824 | 6112 | +4.9% |
| 10k × 20 big ints (~18 digit)    | 7156 | 8023 | **+12.1%** |
| 10k × 8 mixed (4 int/2 text/2 real) | 8971 | 9055 | +0.9% |
| 1k × 2 ints                      |   98 |  108 | +10.7% |

The candidate is **uniformly slower end-to-end**, consistent across all four
passes — worst (+12.1 %) on the big-ints lane, the exact shape where the
isolated `pipe2` conversion won the most (−6.6 %). The isolated win inverts.

## Verdict

**Rejected.** The pipelined-scalar conversion win is real in isolation but does
not survive integration: in `write_json_to_buf` the integer conversion is not
the bottleneck (SQLite value access, per-cell token writes, and buffer
bookkeeping dominate), and the pair-lookahead machinery — the extra branch,
the dual scratch buffers, the duplicated inner token emit — costs more than the
overlapped divide chains save. The two integers of a pair are also fetched
serially through `sqlite3_value_int64`, so the "two independent chains" premise
that made the microbench win never holds on the real path.

Runtime prototype reverted; the three array encoders (`resqlite_test_i64_array_*`)
and the microbench are kept as the durable gate, with a full-range differential
test asserting all three stay byte-identical. No `archive/` tag: the reverted
integration is a trivial lookahead in the `SQLITE_INTEGER` arm, fully described
in the writeup, and the kept test encoders preserve the conversion primitives.
